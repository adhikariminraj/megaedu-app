**A note on how this file was built**: the git history for this project is a single squashed `Initial commit` — there is no granular commit-by-commit history to generate this changelog from mechanically. ## Unreleased

### Changed — Standardize teacher responsibility terminology: Grade Coordinator / Class Teacher (2026-09-01)
An audit of `ClassTeacherAssignment` (Phase 3B) confirmed the schema already fully supports the desired model — one `Teacher` holding multiple Subject Teaching Assignments (`TeacherAcademicAssignment`, already multi-subject/multi-grade/multi-section) plus, independently, an optional grade-wide and/or section-specific `ClassTeacherAssignment` responsibility, all coexisting on the same person with no elevated authority over other teachers. The only real gap was terminology: the grade-wide variant (`sectionId: null`) was inconsistently called "Grade Class Teacher" or just "Class Teacher (whole grade)", and the section-specific variant (`sectionId` set) was called "Section Teacher" — both user-facing terms now retired in favor of **Grade Coordinator** (grade-wide) and **Class Teacher** (section-specific).

No schema change, no migration, no field rename, no new model. `ClassTeacherAssignment` remains the internal model name and `requireClassTeacher()` remains the authorization function name — only user-facing labels, error messages, doc-comments, and documentation changed. The "no teaching hierarchy" principle is unaffected: a Grade Coordinator carries a coordination responsibility only, with no authority over other teachers' assignments, exactly as before.

**Verified**: `npx tsc --noEmit` clean; `npm run db:verify:demo` still 100% passing (no logic touched); live-tested the School Admin's `/dashboard/academics` panel and a Teacher's own dashboard, confirming the new labels render correctly and assignment creation/removal/overlap behavior is unchanged; a full-codebase sweep confirmed zero remaining "Grade Class Teacher" or bare "Section Teacher" strings outside this changelog's own historical entries below.

Updated `AcademicStructureClient.tsx`, `TeacherDashboard.tsx`, `attendance/page.tsx`, `EvaluationsClient.tsx`, `class-teacher-assignments/route.ts`, `authorize.ts`, `schema.prisma` (comments only), `seed-demo.ts` (comments only), `docs/ACADEMIC_OPERATIONS.md`, `docs/API.md`, `docs/ASSESSMENT_AND_EVALUATION.md`, `docs/AUTHENTICATION_AND_AUTHORIZATION.md`, `docs/DATABASE.md`, `docs/DEMO_DATA.md`, `docs/GRADES_AND_PROMOTION.md`, `docs/KNOWN_GAPS.md`, `docs/PRODUCT_RULES.md`, `docs/PROJECT_OVERVIEW.md`, `docs/USER_ROLES.md`, both master docs, and this changelog.

### Added — Simplify assessment system setup with guided wizard (2026-08-31)
The original `/dashboard/assessment-frameworks` editor (grading scales, frameworks, periods, components, and grade/subject assignment, each as its own explicit action) remained fully correct but asked a School Admin to understand the whole 3D-1 data model — grading scale vs. framework vs. assignment — before creating a single usable marking scheme. A guided, 6-step "Create Assessment System" wizard was added on top of it, with no new API routes: the wizard sequences the exact same existing write calls the editor already made (an optional `POST /grading-scales` only when a new scale is being defined inline, then `POST /assessment-frameworks` with its nested periods/components in one request, then `POST /assessment-framework-assignments`), just walked one decision at a time — name it; define terms or one overall period; build the assessments table; choose how results should display (marks/grade/descriptive, reusing or defining a grading scale); choose where it applies (grade-default or a subject override); review and confirm.

`/dashboard/assessment-frameworks` itself is now the landing page: a "Your Assessment Systems" list, a prominent wizard call-to-action, and the original full editor collapsed underneath as an "Advanced management" disclosure — still there, still fully functional, for anything the wizard's guided flow doesn't cover (editing an existing framework's structure, managing grading scales directly, reassigning).

**Verified live** as School Admin: walked the wizard through to completion for a new grading scheme and confirmed it produced the identical `AssessmentFramework`/`AssessmentComponent`/`AssessmentFrameworkAssignment` rows the original editor would have produced for the same input; confirmed the "Advanced management" section still performed every pre-existing action (component edit/delete, grading-scale edit) unchanged; confirmed a non-admin Teacher was redirected away from `/dashboard/assessment-frameworks` before either the wizard or the advanced editor rendered, exactly as before this change.

Updated `docs/ASSESSMENT_FRAMEWORK.md`, `docs/PROJECT_OVERVIEW.md`, `docs/KNOWN_GAPS.md`, and this changelog.

### Added — Improve Class Overview roster and ranking (2026-08-31)
The per-grade Promotion page (`/dashboard/grades/[schoolGradeId]`) previously showed only the narrow, `ENROLLED`-only Promotion-action roster — a student already decided `REPEATED` or `COMPLETED` for the current session simply vanished from the page, even while still physically present in the grade for the rest of the school year. Investigating this surfaced a real, live bug: a genuine seed-data student with an already-recorded current-session decision was invisible on a page meant to show who's currently in the grade.

Fixed by introducing `CURRENT_ROSTER_STATUSES` (`src/lib/gradeHistory.ts`) — `["ENROLLED", "COMPLETED", "REPEATED"]` — as the shared, authoritative definition of "currently in this grade," now used identically by the Grades index's own enrolled-count card and the Class Overview roster. `TRANSFERRED`/`LEFT` remain excluded, since those students have genuinely left the school. The Promotion-action panel itself was deliberately left unchanged — it still only accepts a decision on a still-`ENROLLED` row, enforced server-side by the `grade-decisions` route independently of what the roster displays.

On top of the corrected roster, the page now shows: the grade's Teachers and the Subjects they teach; students grouped by Section (with an "Unassigned" group for anyone with no current section), each showing a per-section, display-only sequential Roll No.; a "Repeated" badge derived live from each student's own `GradeHistory`, never inferred or guessed; and a grade-wide Top 5 ranking — computed once across the whole grade's roster, then grouped for display — reusing the existing assessment calculation engine (`fetchAssessmentResults()`, `computeUnweightedGPA()`, and a new fallback, `computeUnweightedAveragePercentage()`, for a student with no GPA-eligible subject), filtered to published results only.

**Verified live**: the Grades index card and the Class Overview page produced the identical current-roster count for a mix of a fresh admission, a genuinely repeated student, an unassigned student, and the already-`REPEATED` seed-data student, with a separately created `TRANSFERRED` student correctly excluded from both; a Section D student (90.0%) held Rank 1 while a Section A student (60.0%) held Rank 2 on the same grade-wide ranking; the Promotion-action panel continued to silently skip the already-decided student exactly as before, confirming its narrower eligibility was untouched by the roster broadening.

Updated `docs/GRADES_AND_PROMOTION.md`, `docs/ASSESSMENT_RESULTS.md`, `docs/PRODUCT_RULES.md`, `docs/PROJECT_OVERVIEW.md`, `docs/KNOWN_GAPS.md`, and this changelog.

### Added — Phase 3D-2/3/4: Assessment Results, Publishing, Report Cards (2026-08-30)
A read-only investigation (schema, `authorize.ts`, `evaluation.ts`'s audit/share mechanism, `UnitTest`/`UnitTestResult`, `academicProgress.ts`, `AcademicProgressPanel.tsx`, and — deliberately, before designing the Report Card — `Certificate`/`certificateView.ts`) preceded a complete architecture design covering the entire remaining Phase 3D as one integrated system, approved before any code, then implemented per that approval. Built additively on Phase 3D-1 — three new models, one new field on an existing 3D-1 model, no other schema changes.

1. **`AssessmentComponentResult`/`AssessmentComponentResultAudit`/`AssessmentResultPublication`** — per-student component results (`PENDING | EVALUATED | ABSENT`), an append-only correction log written only once a subject is published, and a subject-level (`gradeSubjectId` + `studentId`) draft/publish gate. `GradingScaleBand.isPassing: Boolean?` added, never inferred from label text.
2. **Lazy result creation** — a deliberate divergence from `UnitTestResult`'s eager-roster pre-creation, reasoned through explicitly: `AssessmentComponent`, unlike `UnitTest`, has no single creation moment safe to snapshot a roster against, since components can be added to an already-assigned, reusable framework. The marks-entry page computes a virtual roster (`GradeHistory` + left-join) instead.
3. **`src/lib/assessmentResults.ts`** — the central calculation engine: `computeComponentContribution()` (MARKS direct, GRADE via the matched band's percentage midpoint — explicitly not `gradePoint` — DESCRIPTIVE always excluded, ABSENT always zero), `aggregateGroup()` (one function for both period-scoped and framework-level aggregation), `lookupGrade()`, `computeUnweightedGPA()`, `fetchAssessmentResults()`, `correctComponentResult()`, `buildReportCard()`. Nothing is cached — every total, percentage, and grade is calculated on read.
4. **Publishing workflow** — `requireSchoolAdmin(...) || requireTeacherAssignment(...)` (the identical composition `StudentEvaluation` sharing already uses); blocked server-side while any non-`DESCRIPTIVE` component is still `PENDING`; bulk; a correction to an already-published result is audited but never reverts the publication to `DRAFT` (explicit, approved decision, matching `StudentEvaluation`'s own precedent).
5. **Three integrity guards added to existing 3D-1 routes** (not new routes — genuine integration, not a disconnected sub-phase): the component `PATCH`/`DELETE` routes lock `maxMarks`/`entryMode` once results exist; the assignment `DELETE` route rejects deletion once results/publications reference it; the grading-scale `PATCH` route locks the full `bands` set once any published result uses that scale.
6. **`/dashboard/assessment-results`** (landing + per-subject entry/publish UI) and **`/dashboard/report-card/[studentId]`** (live view, reusing `fetchAcademicProgress()` for attendance/evaluations rather than re-querying) — new pages. `fetchAssessmentResults()` integrated into all three existing `dashboard/page.tsx` call sites and rendered via a new section on the shared `AcademicProgressPanel.tsx`.

**A real bug was caught and fixed during verification, not after**: `lookupGrade()`'s original inclusive-both-ends boundary check made a percentage exactly on a shared band boundary (e.g. 80%) match two bands simultaneously, resolved silently by array order. Fixed to lower-inclusive/upper-exclusive before this phase was considered complete, then re-verified.

**Verified live end-to-end** as School Admin and an assigned Teacher, through the actual UI, direct API calls, and the pure calculation functions: all four `entryMode`/`status` combinations entered and correctly aggregated across both a flat (no-period) and a two-period framework, matched exactly against manual calculation on the live Report Card (Mathematics 77/90 = 85.6% = A; Science 160/200 = 80.0% = A via two periods summing correctly; GPA 3.60); marks-only and descriptive-only frameworks confirmed via the calculation engine directly (percentage-with-no-grade, and no-numeric-result-at-all, respectively); publish correctly blocked while incomplete (`published: 0, skipped: 1`) and succeeded once complete; a correction to a published result produced exactly one audit row (25→27) with the publication remaining `PUBLISHED`; a Teacher assigned to Mathematics/Science received `403` on IT (unassigned); a Parent received `403` on every write route attempted directly; Student, Parent, and the Student's own Report Card each showed only published subjects, while the Staff view (Student Profile) showed all three with publication status labeled; all three integrity locks rejected real violations (`409`) while cosmetic edits (renaming) remained allowed.

All verification data (5 frameworks, 4 grading-scale bands, 3 assignments, 9 results, 1 audit, publications, 2 temporary `TeacherAcademicAssignment` rows) and every temporary verification script were cleaned up afterward; before/after row counts confirmed the school's real `Student`/`Teacher`/`User` data (1/2/7) and Bimla's 3 pre-existing academic assignments were unaffected throughout. Typecheck passed clean (excluding the pre-existing, unrelated `prisma/backfill-certificates.ts` issue) at every checkpoint.

**Known, deliberate scope decisions, not oversights**: no subject-credit/weighting concept (GPA is explicitly unweighted); `isPassing` reserved for a future reference display, not read by any promotion logic yet; no `GET` list API routes; no `UnitTest` integration; no PDF export or persisted Report Card snapshot. See [KNOWN_GAPS.md](KNOWN_GAPS.md).

**Deliberately out of scope**, per the approved design: automatic promotion/pass-fail decisions, subject-credit weighting, PDF report cards, and any change to `GradeHistory`/`recordGradeDecision()`/the Certificate system.

New `docs/ASSESSMENT_RESULTS.md` plus updates to `API.md`, `DATABASE.md`, `PRODUCT_RULES.md`, `PROJECT_OVERVIEW.md`, `KNOWN_GAPS.md`, and this changelog.

### Added — Phase 3D-1: Assessment Framework Foundation (2026-08-30)
A read-only investigation and design-review pass (schema, `authorize.ts`, `academicProgress.ts`, `evaluation.ts`/`attendance.ts`/`gradeHistory.ts`'s audited-write-path pattern, and the `UnitTest`/`UnitTestResult` precedent) preceded any code, per explicit instruction, and produced a design proposal reviewed and approved before implementation. Built additively on the existing Phase 2/3A/3B/3C architecture — six new models, no changes to any existing model's columns.

1. **`AssessmentFramework`/`GradingScale`** — reusable, school-wide templates, deliberately NOT session-scoped like `GradeSubject` (a flagged, approved departure from the originally-sketched hierarchy — re-entering a full marking scheme every session would be a much heavier cost than re-picking a subject from a catalog). `AssessmentPeriod` (optional grouping) and `AssessmentComponent` (`maxMarks` + `entryMode: MARKS | GRADE | DESCRIPTIVE`) belong to a framework; `GradingScaleBand` belongs to a `GradingScale`.
2. **`AssessmentFrameworkAssignment`** — the only session-scoped model, binding a framework to `(academicSession, schoolGrade)`, optionally narrowed to one `gradeSubject` as a subject override. Resolution (`resolveFrameworkAssignment()`, `src/lib/assessmentFramework.ts`): subject-override first, grade-default as fallback — the same nullable-scope-discriminator idiom already used by `TeachingUnit.sectionId`/`StudentEvaluation.gradeSubjectId`/`ParentTeacherMeeting.gradeSubjectId`.
3. **`maxMarks` unifies "weight" and "marks" into one field** — a component worth 10% and a component worth 10 raw marks are the identical shape; only `entryMode` (how a student's eventual result gets recorded, Phase 3D-2) differs. A deliberate simplification over the two-parallel-systems framing in the original brief.
4. **Two more NULL≠NULL uniqueness gaps, both pre-checked from the start** (`src/lib/assessmentFramework.ts`'s `assignmentCollisionExists()`/`componentCollisionExists()`) — grade-default `AssessmentFrameworkAssignment` collisions and framework-level (`periodId: null`) `AssessmentComponent` name collisions, the same recurring class already fixed three times elsewhere in this schema.
5. **School-Admin-only write routes** under `/api/schools/[id]/{grading-scales,assessment-frameworks,assessment-framework-assignments}...` (plus nested `periods`/`components` sub-routes) — `requireSchoolAdmin` gating throughout, no teacher-facing action in this phase.
6. **`/dashboard/assessment-frameworks`** — School Admin configuration UI: create/toggle grading scales and frameworks (with nested periods/components in one request), add/remove periods and components on an existing framework, and assign a framework to a grade or subject for the active session. Linked from the School Admin dashboard as a new "Assessment Frameworks" card.

**Verified live end-to-end** as School Admin, through the actual UI and direct API calls, then as a non-admin Teacher for the negative cases: created all four real-world marking structures from the design brief — a weighted-grade framework (`GRADE`-mode components summing to 100), a marks-based framework (`MARKS`-mode components, 5/5/5/5/80), a term-based framework with two periods (`Term I`/`Term II`) each containing identically-named components with no collision, and a Computer subject-override framework (Theory 50/Practical 50) — with zero special-casing required by the model. Assigned frameworks to Class 9 (default) and Class 9+IT (override), Class 4 (default), and Class 10 (default); confirmed `resolveFrameworkAssignment()` correctly fell back to the default for Mathematics (no override), correctly returned the override for IT, and correctly resolved the grade-only case. Confirmed `409` on a duplicate grade-default assignment, a duplicate subject-override assignment, and a duplicate framework-level component; confirmed `400` on two identically-named, period-less components submitted together in one framework-creation request, before any row was created. Confirmed a logged-in, approved Teacher received `403 {"error": "Forbidden"}` from all four write routes attempted directly via `fetch()`, and was redirected away from `/dashboard/assessment-frameworks` before any page content rendered.

All verification data (4 frameworks, 2 periods, 20 components, 1 grading scale, 2 bands, 4 assignments) and every temporary verification script were cleaned up afterward; before/after row counts confirmed the school's real `Student`/`Teacher`/`User`/`School` data was unaffected throughout (unchanged at 1/2/7/1). Typecheck passed clean (excluding the pre-existing, unrelated `prisma/backfill-certificates.ts` issue) at every checkpoint.

**Known, deliberate scope decisions, not oversights**: framework structural edits are unrestricted in this phase (no marks exist yet to invalidate — must be revisited in 3D-2); no `GET` list API routes (every read goes through the config page's own Prisma queries); `UnitTest`/`UnitTestResult` untouched and not superseded — a deliberately separate, parallel system. See [KNOWN_GAPS.md](KNOWN_GAPS.md).

**Deliberately out of scope**, per the approved Phase 3D-1 design: marks entry, weighted/GPA aggregation, term/annual result computation, report card generation, and any connection to `GradeHistory`/promotion — reserved for Phase 3D-2 through 3D-5, each to be designed and approved separately.

New `docs/ASSESSMENT_FRAMEWORK.md` plus updates to `API.md`, `DATABASE.md`, `PRODUCT_RULES.md`, `PROJECT_OVERVIEW.md`, `KNOWN_GAPS.md`, and this changelog.

### Added — Phase 3C-1: Teacher Qualitative Evaluation & Parent-Teacher Meetings (2026-08-30)
A read-only architecture investigation (twice — a broad Phase 3C survey, then a focused design pass on these two specific features) preceded any code, per explicit instruction. Built additively on the existing Phase 2/3A/3B architecture — `AcademicSession`, `GradeHistory`, `GradeSubject`, `TeacherAcademicAssignment`, `ClassTeacherAssignment`, `requireTeacherAssignment()`/`requireClassTeacher()` — with two new models and no changes to any existing model's columns.

1. **`StudentEvaluation` + `StudentEvaluationAudit`** (`src/lib/evaluation.ts`) — a teacher's narrative evaluation of a student. General (`gradeSubjectId: null`, Class/Section Teacher) vs. Subject (`gradeSubjectId` set, Subject Teacher) is derived entirely from that one nullable field — no separate type field, no parallel model. Freely editable while private; the moment it's shared with **either** a Parent or a Student, `updateEvaluationRemarks()` starts pairing every subsequent edit with a `StudentEvaluationAudit` row in the same transaction. `visibleToParent`/`visibleToStudent` are two fully independent gates with independent timestamps — sharing with one never affects the other. Sharing is one-way (no un-share), matching `Certificate` issuance's existing "permanent once released" precedent. The familiar `NULL ≠ NULL` unique-index gap (already hit twice before, in `TeacherAcademicAssignment` and `ClassTeacherAssignment`) was pre-checked explicitly in the create route from the start this time, not discovered via a live bug.
2. **`POST /api/schools/[id]/students/[studentId]/evaluations`** (create) and **`PATCH /api/schools/[id]/evaluations/[evaluationId]`** (edit/share) — School-Admin/Teacher parity throughout, matching every other Phase 3 write route; a School-Admin-attributed evaluation has its named `teacherId` independently validated via two new exported `authorize.ts` helpers, `teacherHoldsSubjectAssignment()`/`teacherHoldsClassAssignment()` (the first helpers in that file to check a *named* teacher rather than the session's own user).
3. **`ParentTeacherMeeting`** — periodic (bulk) and occasional (single) meetings through the identical model and the identical route (`POST /api/schools/[id]/meetings`, `{meetings: [...]}`), differing only in item count; no recurrence/series concept was built, since nothing in the approved design asked for one. Every item resolved/validated before the transaction opens — the Postgres-safe pattern already used by `grade-decisions`/the rollover sweep, deliberately not the SQLite-only catch-mid-transaction pattern. School-Admin/Teacher-initiated only; Parents are read-only recipients this phase. `PATCH /api/schools/[id]/meetings/[meetingId]` records status/outcome/an optional link to a prepared `StudentEvaluation` (`linkedEvaluationId`, plain FK, not audited).
4. **Parent-Teacher Meetings are structurally Parent-only** — `fetchParentMeetings()` (`dashboard/page.tsx`) is called exclusively from the Parent branch, deliberately kept out of the shared `fetchAcademicProgress()`/`AcademicProgressPanel` used by both Student and Parent for evaluations/attendance/progress/tests, so there's no code path where a Student's own render could ever touch this table, now or by future accident.
5. **Read-side UI** — a new `/dashboard/evaluations` page (General Evaluations + meeting scheduling/outcome-recording, mirroring `/dashboard/attendance`'s existing grade/section picker) for School Admin and Class/Section Teachers; a new "Subject Evaluations" panel added to the existing `/dashboard/academics/[gradeSubjectId]` page for Subject Teachers; a new "Teacher Evaluations" block in the shared `AcademicProgressPanel` for Student/Parent (audience-filtered); a new, dedicated "Parent-Teacher Meetings" section on `ParentDashboard.tsx` (not shared with Student).

**Verified live end-to-end**, as School Admin, a Class/Section Teacher (Demo Teacher), and a Subject Teacher (a throwaway test teacher), through the actual UI and direct API calls: created a General and a Subject evaluation; confirmed 0 audit rows on a private edit and exactly 1 on the first edit after sharing with Parent, with correct before/after remarks; shared the same evaluation with Student independently and confirmed both timestamps set separately; confirmed a duplicate general-evaluation attempt returned `409`; confirmed a Subject Evaluation shared with Student only was visible on the Student's dashboard and **confirmed absent** from the Parent's dashboard for the same child, while a General Evaluation shared with both appeared on both; bulk-scheduled 2 meetings in one request as School Admin on behalf of a named teacher; confirmed an unauthorized attribution attempt was rejected; confirmed a Subject Teacher could self-schedule within their own scope; marked a meeting `COMPLETED` with outcome notes and a linked evaluation, confirmed both persisted correctly; cancelled a different meeting; and — the key structural requirement — confirmed a Student whose evaluations and meetings both existed and were fully populated saw their shared evaluations but **no Parent-Teacher Meetings section anywhere on their own dashboard**. Also verified, as an unrelated Teacher via direct `fetch()` calls: `403` on editing another teacher's evaluation, `403` on creating a Subject Evaluation for a subject not taught, and a rejected/skipped attempt to schedule a meeting "as" a different named teacher.

All throwaway test data (one student, one teacher, two evaluations, one audit row, three meetings, one parent-child link) and every temporary verification script were cleaned up afterward; the school's real `Student`/`Teacher`/`TeacherAcademicAssignment`/`ClassTeacherAssignment`/`ParentStudent` data was confirmed unaffected, before and after, by exact row-count comparison. Typecheck passed clean (excluding the pre-existing, unrelated `prisma/backfill-certificates.ts` issue) at every checkpoint.

**Known, deliberate scope decisions, not oversights**: meeting-scheduling UI exists only on the General Evaluations page, not yet on the Subject Evaluations panel (the backend fully supports it, verified directly); `ParentTeacherMeeting.outcomeNotes` is not audited (only `StudentEvaluation.remarks` was required to be); no un-share path for evaluations; no parent-initiated meeting requests. See [KNOWN_GAPS.md](KNOWN_GAPS.md).

**Deliberately out of scope**, per the approved Phase 3C-1 design: formal term-wide examinations beyond Unit/Chapter Tests, continuous/aggregate progress rollups, and any Parent-Teacher Meeting recurrence/series concept — reserved for a later Phase 3C sub-phase.

### Added — School Admin Direct Student & Teacher Management (2026-08-29)
A follow-up closing a real-world gap explicitly called out for the Nepal context: not every student can complete self-registration themselves, so a School Admin needed a way to create the account directly rather than waiting for the student to register and then approving them.
